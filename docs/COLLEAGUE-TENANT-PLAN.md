# 동료별 계정·Notion 목적지·tenant 격리 단계 제안

이 문서는 구조 제안이다. 실제 동료 계정 연결, 권한 부여, 새 자격증명 생성, 외부 데이터 변경은 수행하지 않았다.

## 현재 출발점

현재 live runtime은 서버에서 고정한 단일 담당자와 한 회원 마스터를 전제로 한다. 데모 tenant 구분과 큐 잠금이 있어도, 동료가 임의로 로그인해 안전하게 자기 목적지로 저장할 수 있는 제품 인증·연결 관리가 완성된 것은 아니다. 기존 단일 계정 scope 상수를 복사해 확장하지 않는다.

## 제안할 연결 단위

| 단위 | 필요한 바인딩과 규칙 |
| --- | --- |
| 사용자 인증 | 웹 로그인 사용자와 서버 소유 tenant를 연결한다. 브라우저 요청의 trainerId/목적지 ID를 권한 근거로 신뢰하지 않는다. |
| 회사 연결 | tenant마다 별도 자동화 세션/프로필을 둔다. 정상 회사 계정 응답의 안정 식별자와 담당자 식별자를 승인 시 고정하고, 수집 전후 재확인한다. 쿠키·토큰을 계정 식별자로 추출하지 않는다. |
| Notion 목적지 | tenant별 연결 자격증명과 명시적으로 승인한 database/data-source/필드 ID를 분리한다. 연결 성공과 목적지 소유·공유 범위 확인을 구분한다. |
| 자격증명 보관 | 현재 보관 원칙을 유지하면서 tenant별 참조만 DB에 기록한다. 사용자에게 원문 키를 채팅으로 받거나 기존 키를 재사용·복사하지 않는다. 구체적인 운영 보관 방식은 배포 환경 결정 후 설계한다. |
| 작업과 중복 키 | queue/run/lease/idempotency/operation journal에 tenant와 connection 버전을 포함한다. 회원 UID는 회사 tenant 범위 안에서만 의미가 있으며 전역 키로 사용하지 않는다. |
| Notion 관리 상태 | 외부 페이지 ID뿐 아니라 tenant·목적지·company UID·필드 소유권을 저장한다. 목적지가 바뀌면 이전 작업/일회 승인을 무효화하고 새 미리보기부터 시작한다. |
| 읽기·쓰기 격리 | 모든 조회·캐시·저장·작업 claim에 서버 tenant 조건을 적용한다. DB 수준 방어를 추가할 때는 현재 query 계층과 migration을 함께 검사한다. 기존 스키마가 RLS를 보장한다고 가정하지 않는다. |
| UI 및 로그 | 본인 연결·본인 작업만 노출한다. 로그는 실행 ID와 HMAC 참조/사유만 남기며 회원 원문과 키를 포함하지 않는다. |

## 권장 구현 순서

1. 서버 사용자 인증과 tenant 소유 관계를 정의하고, 기존 단일 사용자 모드를 유지하며 tenant 경계를 테스트한다.
2. 고정 목적지와 일회 실계정 scope를 일반 연결/승인 모델로 분리한다. 이미 소모된 일회 권한은 이전하지 않는다.
3. 일반 메모·설문·템플릿 수집/매핑 공백을 보완하고, 각 필드의 자동 소유/사용자 소유/보류 정책을 정의한다.
4. 동시 편집 문제는 해결됐다고 가정하지 않는다. 사용자 수동 필드를 계속 보존하거나 자동화 전용 속성/별도 데이터 목적지를 선택하는 운영 설계를 결정한다.
5. 다른 tenant의 UID·목적지·페이지·작업 ID를 교차 주입하는 합성 및 DB 회귀 테스트로 읽기/쓰기/재시도/로그 격리를 검증한다.
6. 동료 한 명이 자신의 회사·Notion 연결과 목적지를 명시적으로 승인한 뒤 읽기 전용 미리보기를 실제로 완주한다. 현재 사용자 연결은 그대로 유지한다.
7. 충돌·재실행·부분 실패·목적지 변경·연결 철회 검증 후, 별도로 승인된 제한적 수동 저장부터 시작한다. 예약 실행은 계속 OFF이며 별도 결정 전 활성화하지 않는다.

## 완료 기준

다른 tenant의 계정/목적지로 읽거나 쓰는 경로가 없어야 한다. 계정 바뀜·불완전 목록·UID 누락·지원하지 않는 속성·충돌은 해당 범위를 보류하고 UI/로그에 이유를 남겨야 한다. 실제 동료 계정 검증과 합성 테스트를 별도로 보고하며, 원본·수동 본문·기존 일정 보존과 중복 방지가 확인돼야 한다.
